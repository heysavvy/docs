**User Data** is the current data stored for a given user. It is a JSON object of properties, such as:

- Answers from input components (keyed by the component key).
- Values from [Computed Fields](/features/computed-fields).
- Values from [Experiments](/features/split-testing).
- URL params, automatic data, and other registered keys.

## Types of User Data

| Type | Example | Typical use case |
| --- | --- | --- |
| **Automatic data** | `current_page_key` | Send the user's current page to an API |
| **Answers** | `weight` | Collect details from the user |
| **Computed Fields** | `bmi` | Calculate a value for eligibility or display |
| **Experiment data** | `split_title_length` | Show or hide content by variant |
| **URL params** | `utm_source` | Branch logic based on traffic source |
| **Registered keys** | `access_token` | Store the result of an API request |

## Where User Data is stored

User Data lives in three cascading contexts. If a property is stored in a deeper context, it is also available in the ones above it.

1. **Embeddable context** — the full User Data object inside the Embeddable. Cleared when the user refreshes or closes the tab.
2. **Local Storage context** — a subset stored in the browser. Remembers answers and flow position when the user returns later.
3. **Embeddables Cloud context** — the smallest subset, stored in Embeddables databases for analytics in the Web App.

## Keys and naming

Input components write into User Data using their **component key** as the property name. If an input has the key `name`, User Data looks like:

```json
{
  "name": "John Doe"
}
```

Choose keys carefully — especially for inputs — because they become User Data property names.

### Naming rules

- Use `snake_case`: lowercase letters and underscores only (no numbers, spaces, or special characters).
- Experiment keys must start with `split_`.
- Prefer short, descriptive names that describe the **data**, not the component (for example, `full_name`, not `full_name_input`).

### Keep keys unique

Keys must be unique within an Embeddable, with one exception: multiple inputs that are swapped so only one is visible at a time (for example, two email capture variants in a [split test](/features/split-testing) that both use the key `email`).

## Default User Data

Default User Data sets initial values when an Embeddable loads. Values are stored in `defaults.userData` and applied before the user interacts with the flow.

### Set default values

1. Open the Embeddable **Options** panel in the Builder.
2. Click **Edit default user data JSON**.
3. Add key-value pairs in JSON format.

```json
{
  "user_type": "new_visitor",
  "source": "organic",
  "language": "en"
}
```

Common uses:

- Pre-fill form fields users can change.
- Set starting values for conditions or other logic.
- Attach default tracking metadata for the session.

### How defaults behave on reset

When User Data is reset:

1. Most properties are cleared.
2. System properties (such as `entryId` and `current_page_id`) are preserved.
3. Computed field and experiment keys are preserved.
4. Default User Data values are reapplied.

Defaults do **not** overwrite an existing value for a key unless User Data is reset.

### Limitations

<Warning>
  Do not use defaults for **Computed Field** keys. Computed fields manage their own values; defaults can conflict with the update sequence.
</Warning>

<Warning>
  Do not use defaults for **experiment** keys. Experiments set that data automatically.
</Warning>

<Note>
  Defaults for keys that are not created by components, computed fields, or other features require those keys to be added as **Registered Keys**, so the Embeddable can track them.
</Note>
