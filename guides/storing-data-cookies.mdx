Embeddables uses **Local Storage** to persist [User Data](/features/user-data) in the browser so users can refresh or return later and continue where they left off.

Local Storage is similar to cookies, but differs in capacity, expiration, and whether data is sent with HTTP requests.

## Storage contexts

In the Builder, you choose where each field is stored. The three cascading contexts are:

1. **Embeddable context** — in-memory for the current session only.
2. **Local Storage context** — persists after the tab or browser closes (also available in the Embeddable context).
3. **Embeddables Cloud context** — stored on Embeddables servers for analytics in the Web App (also available in Local Storage and Embeddable contexts).

## Local Storage vs cookies

| Feature | Local Storage | Cookies |
| --- | --- | --- |
| **Capacity** | 5–10MB | About 4KB |
| **Expiration** | Does not expire automatically | Can be set to expire |
| **Sent with requests** | No — stays in the browser | Yes — sent with HTTP requests |
| **Accessibility** | Same-origin only | Can be configured for cross-origin |
| **Manipulation** | JavaScript only | JavaScript or HTTP headers |

### How long Local Storage lasts

Local Storage data remains until the user:

- Clears browser data or cache.
- Uses private or incognito browsing.
- Switches to a different browser or device.

Unlike cookies, Local Storage has no built-in expiration, so users can return weeks or months later and still resume their flow.

### Privacy

Local Storage is generally more privacy-friendly than cookies because it:

- Is not sent automatically with HTTP requests.
- Is limited to the domain that created it.
- Does not enable third-party cookie-style tracking.
